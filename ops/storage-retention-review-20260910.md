# BUZZ NOW 保存容量の調査と整理案（2026-09-10）

状態: 調査・設計のみ。本番履歴の削除・画像の削除はまだ実行していません。

## 確認したこと

- Render の本番DBは約387 MB、Neon の試験コピーは約347 MB。コピーで物理サイズは変わるため、差を削除量とは扱わない。
- traffic_history は約158 MB。2026-09-10の確認で1,136,427件、最古2026-09-03、最新2026-09-10。30日以前の行は0件。30日保存の設定だけでは直近の容量は減らない。
- social_images は約140 MB、social_image_derivatives は約13 MB。画像本体をBase64テキストでDBに格納している。
- refresh_real_traffic_forecast は収集時に全トレンドについて履歴を追加する。値が前回と同じかの判定がない。
- traffic_historyのREALモードのPV等はシグナルから算出する予測値であり、Google Analytics等の実測アクセス数ではない。日次集計も合計PVとはせず、平均・最大・最終予測値と観測数を保存する。
- 公開traffic APIは履歴を通常24件、最大100件参照する。現在値はtraffic_totalsに別保存している。
- source_snapshotsには既に全体約12,000件上限、v9_signal_historyには既に90日保持がある。
- prediction_results全件をもとに累計精度を再計算している。単純に古い結果を消すと精度の意味が変わる。直近100件の予測と結果を結合してモデル調整に使う。
- SNS投稿記録は重複投稿防止、画像は過去の公開URL、トレンド記事は公開URLの維持にも必要。

## 実装の優先順位案

1. traffic_historyの新規書込みを抑制。同一トレンドで値に変化がなく短時間なら履歴を追加しない。定期的な観測点は残す。現在値とupdated_atは従来どおり更新。
2. 日次要約を先に作成・検証したうえで、詳細履歴をトレンドごと最大100件に整理する案を評価。公開APIの上限100件を維持する。日次要約の保存は1年を初期案とし、トレンド数増加も見込んで上限を測定する。
3. 予測の未評価分は保持。評価済み詳細は90日を初期案とし、削除前に日次の件数・的中数等を集計。累計精度と直近精度を区別し、モデル調整用の参照整合性を維持。
4. 公開画像のURLを維持したまま画像本体をオブジェクトストレージへ移す案を調査。別途サービス・費用・認証が必要なため未作成。DBには参照先・形式・サイズ・照合値を残す。先にコピー検証し、その後にDB画像本体を削除する。
5. 投稿済み識別子、記事の公開URL、出典リンクを年齢だけで削除しない。重複投稿防止記録は小さいまま保持。
6. 定期処理は対象件数を事前表示できるdry-run、少量ずつの削除、同時実行防止、集計済み確認、失敗時の記録を備える。Neonの実サイズと増加ペースを監視する。

## 注意

- PostgreSQLの通常DELETEは空きを再利用可能にするが、すぐディスク使用量が減るとは限らない。容量ぎりぎりでテーブルを丸ごと複製する方式は避ける。
- 移設中に失敗した一括置換は旧データと新データが同一トランザクション内で重なるため512 MBを超えた。承認済みのNeon試験コピーの入れ直しと、本番履歴の定期整理は別作業。
- 保存期間・集計内容は上記の設計案。実装・本番削除が完了したとの記録ではない。
